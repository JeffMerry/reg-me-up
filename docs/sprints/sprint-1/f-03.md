## 1. Behavior and invariants

Participant opens public detail → identity and own-registration state loaded → explicit Register → server validates and commits → success/reference → own list/detail. Login return alone must not submit. Organizer direct registration API is denied even if UI control is absent. Requests act only as the current Participant.

Invariants: event ACTIVE count <= capacity; each Participant/event active pair <=1; failed/denied mutation adds no row; successful ID is retrievable after reload/application restart with same DB. All runtime count-changing paths follow [SDS §3](../../system-sds.md). Frontend availability is advisory and stale-data conflict must be handled. BR-01's 1–60 bound applies to newly published events only; an existing event above 60 remains registerable against its stored capacity, subject to the normal F-03 ownership, duplicate, and seat-availability rules. Never clamp a legacy capacity during registration or retrieval; see [SRS DEC-15](../../srs.md).

## 2. API contract

| Method/path | Input / precondition | Success | Expected negatives |
|---|---|---|---|
| POST `/api/events/:eventId/registrations` | Participant session + Origin/CSRF; UUID path; JSON `{}` only; published event | 201 `{data:RegistrationOwn}` after confirmed commit | 401 anonymous; 403 wrong role/CSRF; 422 malformed ID/extra fields; 404 unknown/unpublished; 409 duplicate/full |
| GET `/api/me/registrations?page=1&pageSize=20&eventId=:uuid` | Participant; eventId optional | 200 own RegistrationOwn rows/meta, registeredAt/id DESC; empty match is [] | 401/403; 422 bad query; no arbitrary participantId filter |
| GET `/api/me/registrations/:registrationId` | Participant; UUID | 200 `{data:RegistrationOwn}` | 404 unknown or other Participant's ID; 422 invalid UUID; 401/403 |

Response fields/limits/errors use [SDS §5](../../system-sds.md). RegistrationOwn includes server registration ID/reference, ACTIVE status, registeredAt, current Participant display name and public event details. No arbitrary user-ID endpoint or private registrant list. Public event API never embeds own registration object; UI uses authorized own read.

Conflict precedence after session/role/CSRF/input/resource checks: existing own active pair → 409 ALREADY_REGISTERED with own registrationId, **even if full**; otherwise active count >= capacity → 409 EVENT_FULL. A stale UI must link/retrieve actual existing row; it must not fabricate success/reference.

## 3. Feature SDS and data changes

Use one Prisma interactive `$transaction` at READ COMMITTED and its `tx` for every operation; run parameterized `tx.$queryRaw` to lock the event FOR UPDATE, then use separate statements to check the pair and count after acquiring the lock. Insert only if both pass; throw on failures to roll back and return success only after the transaction resolves. Never use the root Prisma client or a second pool inside the transaction. Unique active pair migration guards concurrent duplicates; event lock and shared writer protocol protect capacity. No check based only on UI or count outside transaction is acceptable.

SYS-01 establishes registrations FK/check/partial-unique/indexes per SDS for shared use, including F-02 count reads; F-03 consumes that baseline and adds a new reviewed migration only if genuinely needed. No cancel/status transition/attendance table or seat counter in Sprint 1. Transaction-client use, Prisma Migrate schema/setup dependency and lock protocol are part of review. No event-edit behavior belongs here.

PostgreSQL lock/statement timeout parameters are 2s/5s; Prisma transaction acquisition/runtime timeouts must be coordinated and their actual behavior verified; known rollback contention/deadlock returns503 TEMPORARILY_UNAVAILABLE. Unknown COMMIT response returns safe503 OUTCOME_UNKNOWN where possible; network timeout also unknown. UI must check own registrations before retry; no automatic POST retry. Fault-injection tests use internal dependencies/DB state, never a public bypass endpoint. Successful response snapshot/count may become stale due later registrations; reload server state for UI.

## 4. UI behavior

UI-03/04/04-D follow [baseline](../../ui-spec.md). Own status is fetched before deciding CTA; if it cannot load, disable register and offer read retry. Already registered takes precedence over Full. Pending disables repeated clicks but does not substitute DB safety. Success shows server reference and own-detail link, then refreshes event/own state.

Full: explain failure/refresh availability; duplicate: read/link existing own registration; unknown outcome: say unconfirmed and offer My Registrations check before a new submit. Own list/detail has loading/empty/error and authorized deep link `/my-registrations?registrationId=:uuid`; changing ID never reveals another person's data. No QR/cancel/attendance states. Modal has label/focus trap/Escape/restore; restart persistence is verified at API/DB level, not just UI local state.
