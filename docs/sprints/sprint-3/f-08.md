# F08 — Owner attendance report by unique participant

Version0.1,27Nov2026. Refs #44/#45; FR09, BR05/10, NFR01/02/06. User confirmed unique-person/current-status policy27Nov; technical contract pending THN4 review. Owner JeffMerry; implementation/tests NOT RUN.

## Definitions and invariants

Count people distinctly **within one event**, not registration IDs, historical rows or accounts globally across events. registered = COUNT DISTINCT participant_id with ACTIVE registration. cancelled = COUNT DISTINCT participant_id with CANCELLED history AND NOT EXISTS ACTIVE for that participant/event. attended = COUNT DISTINCT participant_id whose registration has persisted Attendance. A cancelled-then-reregistered person is registered1/cancelled0; repeated cancellations do not multiply people. A checked-in person is included in both registered and attended; UI must not sum those two as disjoint totals. Under current lifecycle, attended≤registered≤capacity; a contradictory legacy state is reported as a verification defect rather than silently deleting history.

Example P1 CANCELLED,CANCELLED,ACTIVE+attendance; P2 CANCELLED,CANCELLED; P3 ACTIVE yields registered2,cancelled1,attended1. Empty event yields0/0/0. Attendance existence is based on DB records, never status labels, local storage or capacity-minus-remaining alone. Registration, cancellation and attendance histories/IDs remain intact. F08 makes no schema/counting changes to seat allocation and has no write endpoint.

## Feature SDS / reads / privacy

Organizer reads only their own event. Validate event UUID/query and session/role, then use one REPEATABLE READ transaction for owner event lookup, aggregates, distinct-person row selection, total and page. This prevents mixing counts from different snapshots when cancellation/re-registration/check-in occurs concurrently. Do not fetch public data and then return private registrants before owner validation.

Derive the participant roster from distinct participants who ever registered to that event, ordered displayName/participantId ASC for stable ties. Each row shows person displayName, current registration state ACTIVE or CANCELLED, and attended boolean/checkedInAt or null. When ACTIVE exists, select that registration; otherwise use latest CANCELLED by registeredAt/id DESC only to determine current display state. Existing partial ACTIVE uniqueness is retained. Report aggregation must avoid join multiplication caused by many histories/attendance rows; distinct participants are counted in each set. If old inconsistent multiple attendance rows exist, aggregate at person level and preserve source rows; do not quietly claim cleanup.

DTO rows contain only report-needed participantId/displayName/currentStatus/attended/checkedInAt. No email/hash/session data, unrelated event/assignment history or administrative mutation. 401 anonymous/expired;403 Participant/Instructor;404 non-owner or missing event with no private details;422 invalid identifier/pagination/unknown query. No export/CSV/PDF generation/filter/search/chart endpoint in this baseline. Owner may view report before/during/after event; a zero count is distinct from a failed read. This does not grant report access to an assigned Instructor.

## UI and lifecycle

Separate owner Report view linked from My Events with counts explicitly labeled people. Show Registered (current), Cancelled (no current registration), Attended; explain attended is part of registered. Detail list is one person per row with current state/attendance time, stable pagination and Thai display times. Loading/empty/error with explicit retry, unauthorized/missing and expiry clearing private data must be distinct. No synthetic successful count on a failed read. Report is read-only, so refresh retries GET safely. Browser Back/reload/deep link and320/390/1440 keyboard layouts must work; server authorization applies even if links are hidden.
